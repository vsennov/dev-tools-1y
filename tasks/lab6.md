# Лабораторная работа №6. Простые CI-CD пайплайны

## Цель работы

Познакомить студента с простыми средствами автоматизации процесса задач
разработки в рамках работы с системой контроля версий.

## Процесс работы

По ходу выполнения работы фиксируйте промежуточные шаги для каждого этапа. Для
консольных команд в конце каждого этапа копируйте в отчет команды, которые
привели к успеху и их вывод, добавляя небольшое описание.

Для заданий, отмеченных ключевым словом *Узнайте*, выпишите в отчет краткий
конспект информации и укажите используемые источники.

## Этапы выполнения работы

### Базовые хуки в Git на стороне клиента

1. *Узнайте*, к каким операциям и к каким их этапам можно добавить свой код.
   Отметьте, какие операции можно прервать с помощью хуков.
2. Добавьте хук, который проверит код, добавляемый в коммит, на предмет наличия
   запрещенных слов или паттернов. Перечень запрещенного к коммиту контента
   определите самостоятельно (можно, например, отслеживать, что ssh-ключи,
   токены доступа не попадают в репозиторий).
3. Добавьте хук, который каким-то образом проверяет ваше сообщение коммита и
   останавливает процесс фиксации, если что-то не так с сообщением коммита.
4. Приведите в отчете примеры вывода этих хуков, продемонстрируйте их работу.

### Хуки Git на стороне сервера

Этот раздел эмулирует ситуацию, когда у вас есть удаленный сервер, на котором
развернут какой-то проект, и вы хотите автоматизировать развертывание изменений
после доставки. Например, у вас есть сервер, где развернут телеграм-бот; когда
вы вносите изменение в код, вам хочется автоматизировать доставку изменений в
коде и развертывание.

1. Создайте копию вашего репозитория на вашем компьютере. Добавьте копию в
   качестве удаленного репозитория в ваш основной репозиторий. Проверьте (или
   добейтесь того), что вы можете делать `push` в вашу копию.
2. *Узнайте*, каким образом можно конвертировать Markdown-файл в html-файл.
3. Настройте в вашей копии хук, который будет создавать html-версию вашего
   отчета из md-файла по последней версии из указанной ветки (например, `lab6`).
4. Отобразите html-файл в браузере, сделайте `push` в нужную ветку, убедитесь,
   что html-файл корректно отображается и обновляется при отправки изменений
   в репозиторий.

### Сборка с помощью CMake

1. Установите CMake там же, где вы запускаете Make для работ по "Структурам
   данных".
2. *Узнайте* осиновые понятия CMake (проекты, цели, библиотеки, исполняемые
   файлы), выпишите основные конструкции для работы с этими сущностями.
3. Перепишите цели сборки последней выполненной работы по "Структурам данных" c
   Make на CMake, используя следующую архитектуру.

  - Вся функциональность, которая выражена отдельными от основного файла
    классами и функциями объединяется в отдельную библиотеку.
  - Основной файл (labX.cpp) и эта библиотека собираются в исполняемый файл.
  - Каждый тест собирается отдельным исполняемым файлом, к которому подключается
    библиотека.
  - Тесты оформляются с помощью отдельного `CMakeLists.txt` в директории
    `tests/`, где тесты оформляются с помощью CTest, тесты добавляются в
    основной проект как дочерняя директория.

4. Продемонстрируйте, как проводить сборку проекта и запуск тестов с помощью
   `cmake`.

### Автоматизация задач CMake в git

1. Добавьте в ваш репозиторий ветку `dev`.
2. Добавьте хук, который будет на каждый коммит в `dev` прогонять тесты CMake и
   обрывать коммит, если тесты не прошли.
3. Проверьте, что этот хук работает и в случае обычного коммита в `dev`, и в
   случае `merge`.
4. Добавьте хук для сборки библиотеки по коммиту в `dev`.

### Автоматизация с помощью Github Actions

1. *Узнайте* основной синтаксис языка YAML; узнайте, какие конструкции можно
   задавать этим языком.
2. *Узнайте* основные возможности Github Actions; узнайте, какие тарифы доступны
   для использования.
3. Добавьте в ваш репозиторий в Github определения ci-cd пайплайнов для
   автоматизации тех же задач CMake из прошлого раздела.
